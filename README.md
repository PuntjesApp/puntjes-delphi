# puntjes-delphi (experimental)

Two Delphi units for the [Puntjes](https://puntjes.app) loyalty API, generated from the published OpenAPI document
by [mORMot 2](https://github.com/synopse/mORMot2) `mopenapi`. Nobody edits them by hand: a new API version opens a
pull request with regenerated units, and every merge to `main` can make a release.

This repository is experimental. It has no hand-written client layer and no support promise. The units compile with
Free Pascal in CI. They have not been compiled with Delphi's own compiler (`dcc64`) yet; that is a manual step on a
licensed Windows machine.

## What you need

- **mORMot 2 at tag [`2.4-stable`](https://github.com/synopse/mORMot2/releases/tag/2.4-stable)**, with its `src`
  folders on your search path and its static files where mORMot expects them. Units generated by a newer mORMot
  do not compile against 2.4, and these do not compile against an older one.
- Delphi or Free Pascal 3.2.2, as mORMot 2.4 supports them.
- On Linux, OpenSSL 1.1 or 3 for HTTPS. mORMot loads it at run time.

## Install

Download `puntjes-delphi-v<version>.zip` (for example `puntjes-delphi-v0.1.0.zip`) from the [latest release](https://github.com/PuntjesApp/puntjes-delphi/releases/latest),
or the two units on their own, and add `src` to your search path.

Or use [Boss](https://github.com/HashLoad/boss):

```sh
boss install github.com/PuntjesApp/puntjes-delphi
```

Boss installs these units only. Install mORMot 2.4 yourself: its tags are not SemVer, so Boss cannot pin it.

## Quick start

Create API credentials in the Puntjes admin portal. The secret is shown once. It gives full access to your shop's
API, so keep it on a server or a till you control, never in a program you hand to customers.

```pascal
http := TJsonClient.Create('https://puntjes.app', 'api/v1');
puntjes := TPuntjesClient.Create(http);
http.SetBearer(Token('https://puntjes.app'));

// A customer scans their card at the till.
writeln(puntjes.LookupCustomer(card).Data.WalletBalance);

// Record the purchase. Amounts are in cents.
purchase.Identifier := card;
purchase.TotalAmount := 4200;
purchase.IdempotencyKey := ToUtf8(key); // a new GUID per purchase, reused on a retry
writeln(puntjes.SubmitTransaction(purchase).Data.PointsEarned);
```

[`examples/QuickStart.dpr`](examples/QuickStart.dpr) is the complete program, with the token request. Run it with
`PUNTJES_CLIENT_ID` and `PUNTJES_CLIENT_SECRET` set:

```sh
QuickStart <card number> <amount in cents>
QuickStart health
```

## What to expect from generated units

- **A nullable field or a union arrives as a `variant`.** Check it with `VarIsNull` before you read it.
- **An update sends every field, also the ones you did not set.** An unset `variant` field goes out as `null`, and
  the API stores that `null`. So `UpdateCustomerByExternalId` with only `Phone` set also clears the name, the email
  and the date of birth, and `UpdateProduct` with only `Name` set clears the description and the price. Read the
  record first, copy every field you want to keep into the payload, then send it.
- **A request body that the API does not require has an overload without it.** `VerifyRedemption(code)` sends no
  body, and `VerifyRedemption(code, payload)` sends the payload. The same goes for the customer, card, product and
  voucher calls whose body is optional in the API spec.
- **The answer types called `TDtoPuntjes<N>` can be renamed in any release.** `mopenapi` numbers each unnamed
  answer wrapper, so a new endpoint can move the numbers after it. Do not declare a variable of such a type. Read
  `.Data` in the expression, as the quick start does, and keep the named records such as `TCustomerData`. This is
  why the version stays below 1.0.
- **The token is yours to fetch and renew.** A token lasts one hour. On a 401, fetch a new one and call
  `SetBearer` again.
- **Nothing retries.** On a network error or a 5xx, send the same request again with the same `idempotency_key`.
  The API records the purchase once.
- **An error answer with a documented status raises `EErrorResponse`.** Its `Error.Error` record carries the API's
  `Code` and `Message`. Any other status, such as a 502 from a proxy, raises a plain `EJsonClient` without that
  record.

The [Puntjes API documentation](https://docs.puntjes.app/docs/api-overview) describes every endpoint and error code.

## How the units are built

| Script | Does |
|---|---|
| `scripts/mormot.sh` | Clones mORMot at `2.4-stable` into `.mormot`, refuses a commit other than the pinned one, and unpacks the static files after a sha256 check |
| `scripts/generate.sh` | Builds `mopenapi` and writes `src/` from `spec/api.json` |
| `scripts/compile.sh` | Compiles the quick start with `fpc -Mdelphi`, and fails on any warning or note in a generated unit |

`spec/SOURCE` names the published spec the units come from. On a machine without Free Pascal, run the scripts in a
container:

```sh
docker run --rm -v "$PWD:/w" -w /w ubuntu:24.04 sh -c \
  'apt-get update -qq && apt-get install -y -qq fpc git curl ca-certificates >/dev/null && scripts/mormot.sh && scripts/generate.sh && scripts/compile.sh'
```

CI regenerates the units on every pull request and fails when they differ from `src/`, then compiles the quick
start.

One local trap: mORMot 2.4 misreads an answer that has neither a `Content-Length` nor chunked framing, which is
what PHP's built-in development server sends. The Puntjes API sends a length, so this only matters against a local
`php artisan serve`.
